# Post-logo conversation, automatic artwork routing and publishing guidance

Implemented and verified the supported automatic-apply path in the existing Copilot conversation. **579 tests passed, zero failed and zero pending across 52 unique test files.** Actual desktop/mobile Edge verification used isolated local data, real controllers and the existing deterministic renderer, with a mocked AI provider.

The local API must be restarted to load its newly configured renderer path. No running customer API was restarted, and no production/staging configuration was changed.

## Confirmed cause

The reported sentence was generated by `swagGuidance()` when `automaticArtworkAvailable === false`. `publicState()` derives that flag from `rendererConfigured()`, which checks `SWAG_RENDERER_EXECUTABLE`. This branch does **not** inspect an individual product's print area. At the start of this task, the local API `.env` had no renderer executable setting and the command environment had no setting either. The private renderer bundle and installed Edge executable already existed.

Two conflicting backend hints reinforced the wrong route: uploaded artwork always exposed `nextStep: save_then_editor`, even when the renderer was configured, and the embedded preparation-tool description said publishing uploaded artwork required the visual editor. The frontend also interpreted error-message words such as “automatic” or “designer” as a reason to show manual controls, which could confuse a transient failure with an eligibility failure. Finally, a post-upload “Yes” had no deterministic contextual preparation route.

These causes were reproduced with isolated state. No live `ai-test` conversation or customer catalog data was queried or changed. The code path explains the exact reported wording; it does not establish that every product in the customer's original selection is eligible. Product-level eligibility continues to be evaluated by the existing real inspection/preparation service.

## Implemented behavior

1. **Local renderer configuration:** appended only `SWAG_RENDERER_EXECUTABLE="C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe"` to `apps/api/.env`. Every original configuration byte was preserved. The existing opt-in configuration remains in place; no automatic browser discovery or sandbox relaxation was added. [Configuration evidence](local-renderer-config.json).
2. **Consistent automatic routing:** a configured upload now projects `approve_artwork`; the embedded tool description and model guidance explain the existing Apply PREPARE route, with manual placement reserved for actual limitations or requested advanced editing. Public MCP schemas and execution contracts are unchanged.
3. **Natural upload acknowledgement:** “I've received your logo. Would you like me to apply it to your selected products?” appears in the same persisted chronological conversation. The normal uploaded-logo step has one optional **Review artwork application** action. The six-action menu and More design options are removed from this presentation. Uploading does not prepare or execute a business write automatically.
4. **Contextual approval:** “Yes”, “Apply it”, “Apply to all” and “Only apply it to the polo” use the existing authorized, revision-bound Apply preparation. Subset targeting resolves only verified selected identities and clarifies ambiguity. A typed response never executes. Repeated requests reuse a pending bound approval; an unresolved consumed operation is not replayed.
5. **Actual eligibility:** mixed results name unsupported products and their real reasons in a partial-application approval. Zero eligible targets explain the inspection reason and offer the designer. Renderer busy/unavailable errors remain distinct from product ineligibility. The frontend uses the actual error code instead of keyword matching.
6. **Saved mockups and follow-up:** the committed receipt acknowledges actual application, distinguishing subset results. The existing saved-preview gallery displays persisted product-specific mockup URLs. Products without a saved customized preview are identified rather than represented with catalog photography. A persisted step mode places “Do these designs look good? Would you like to publish them or make changes?” **below** the current mockups. There are no Save Design/Reload controls in this normal successful path.
7. **Publishing guidance:** “Looks good” on branded designs asks whether to publish the collection or a selected product. A clear “Publish my collection to AI Store” resolves the authorized exact store and prepares one final full-collection preview directly. Missing stores are requested. Confirm & Publish remains the separate user-click execution gate.
8. **One-product requests:** this backend publishes collections. A one-product request explains the existing separate one-product collection alternative and asks which scope the user wants. It does not remove products, clone a collection, or prepare the full collection silently. A targeted conversational guard retains this clarification through ambiguous later answers, Next/store selection, and provider tool attempts. Explicit full-collection intent clears it.
9. **Capabilities retained conversationally:** changing/replacing the logo uses the existing + picker; adding another product preserves the upload and selections; Skip/Not now uses the existing no-artwork path; Save for later prepares only save. Open designer prepares a save when required. For an unchanged authorized saved design it offers the existing workspace-aware designer link without another persisted-write confirmation. Paused resume, receipt recovery and the old no-artwork progression remain intact.

## Preserved safeguards and remaining limitations

- Renderer/geometry, product inspection rules, asset persistence, per-product artwork scoping, saved mockup consistency, transaction execution, durable receipts, idempotency, actor/tenant authorization and financial services were not changed. Existing real-renderer tests cover subset application, legacy shared-logo preservation, failed/uncertain outcomes and Save for Later resume.
- Automatic application still requires a valid installed browser, matching private renderer build, supported product print area/dimensions and readable permitted raster imagery. An expired/inaccessible upload still requires replacement. This task does not widen eligibility or asset access.
- This local API needs a **restart** to read the appended renderer configuration. Production/staging must retain their own explicitly managed renderer setup; neither was modified.
- Product-level eligibility for the user's original live selection was not asserted from isolated fixtures. The real preparation service remains authoritative for that selection.
- Single-product publication is not a new independent backend capability. The safe alternative is to explicitly start a separate one-product collection through the existing workflow. No automatic cloning/forking was added.
- Complex natural-language variants still use the existing model/tool workflow. Deterministic common intents and mocked-provider integration are verified; live Claude phrasing quality is unverified.
- Existing TypeScript errors remain. No new blocker was found for the supported automatic path in controlled local testing.

No production/staging writes, real customer publication, real emails, wallet deductions, commit, push, merge, reset, deployment or Git remote changes were performed.
